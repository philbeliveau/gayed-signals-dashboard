# Story 4.0e: API Route Consolidation

**Epic:** 4.0 Data Pipeline Restructuring
**Story ID:** 4.0e
**Priority:** High
**Estimated Effort:** 5 days
**Status:** ✅ Ready for Review

---

## Story

**As a** frontend developer
**I want** a unified `/api/v2/signals` endpoint served by Railway backend that consolidates all signal data access
**So that** I have a single, consistent interface for fetching signals from Railway PostgreSQL with caching and automatic failover

---

## Context

Current API routes are fragmented across multiple endpoints (`/api/signals/`, `/api/content/substack/`, `/api/content/unified/`) with inconsistent interfaces and no centralized orchestration. This story creates a unified V2 API that leverages SignalOrchestratorV2 for intelligent data sourcing while maintaining backward compatibility.

### Request Flow

1. **Request Reception**
   - Parse and validate query parameters
   - Authenticate API key
   - Check rate limits
   - Log request

2. **Orchestration**
   - SignalOrchestratorV2 selects optimal source
   - Check circuit breaker status
   - Query sources in priority order
   - Apply timeout per source

3. **Data Processing**
   - Score data quality
   - Filter and sort results
   - Apply pagination
   - Add metadata

4. **Response**
   - Format response (V2 or legacy)
   - Compress payload
   - Set cache headers
   - Return with metadata

   - **Solution:** Coalesce identical requests in-flight

   - **Solution:** Proactive cache warming for frequently accessed signals
   - **Impact:** 20-30% improvement in average response time
   - **Effort:** Medium (1-2 days)

   - **Issue:** 100 entry limit may cause excessive evictions
