## Story

**As a** quantitative analyst,
**I want** the backtesting system to use the UnifiedDataService exclusively for all market data,
**so that** I can trust that all backtesting results are based on validated, real market data with proper quality scoring and provenance tracking

## Acceptance Criteria

1. [ ] UnifiedDataService fully integrated into backtesting orchestrator
2. [ ] All synthetic data generation code removed completely
3. [ ] Data quality validation before any backtest starts (minimum score: 0.8)
4. [ ] Data completeness checks with clear error reporting
5. [ ] Data provenance tracking for all backtest data
6. [ ] Proper error handling when real data unavailable
7. [ ] Data availability service that suggests valid date ranges
8. [ ] PostgreSQL persistence for all fetched market data
9. [ ] Redis caching for frequently accessed data
10. [ ] 100% real data usage - zero synthetic data in production

## Dev Notes

### Testing Standards

**Testing Requirements:**
- Test files location: `apps/web/src/domains/backtesting/__tests__/`
- Use Jest for unit tests
- Use real API responses for integration tests (no mocks for data fetching)
- Minimum 90% code coverage for new code
- Test data validation with both valid and invalid data
- Test error scenarios when data is unavailable

**Key Testing Scenarios:**
- Data quality below threshold (score < 0.8)
- Missing data for requested date range
- Partial data availability
- Data source failures
- Cache hit/miss scenarios

### Architecture Context

**UnifiedDataService Location:** `domains/data-pipeline/src/services/UnifiedDataService.ts`

**Key Methods to Use:**
```typescript
// Fetch market data with validation
async fetchMarketData(symbols: string[], options?: FetchOptions): Promise<MarketDataResult>

// Validate data quality
async validateDataQuality(data: MarketData[]): Promise<ValidationResult>

// Track data provenance
async trackProvenance(data: MarketData[]): Promise<void>
```

**Data Quality Scoring:**
- Score range: 0-100
- Minimum acceptable: 80
- Factors: completeness, freshness, consistency, outliers

**PostgreSQL Schema:**
```sql
-- Market data table
CREATE TABLE market_data (
  id SERIAL PRIMARY KEY,
  symbol VARCHAR(10) NOT NULL,
  date DATE NOT NULL,
  close DECIMAL(10, 2) NOT NULL,
  volume BIGINT,
  source VARCHAR(50),
  quality_score DECIMAL(3, 2),
  created_at TIMESTAMP DEFAULT NOW(),
  UNIQUE(symbol, date)
);

-- Data provenance table
CREATE TABLE data_provenance (
  id SERIAL PRIMARY KEY,
  data_id INTEGER REFERENCES market_data(id),
  source VARCHAR(50),
  fetch_time TIMESTAMP,
  transformations JSONB,
  quality_metrics JSONB
);
```

**Critical Implementation Notes:**
1. NEVER generate synthetic data - fail gracefully instead
2. Always validate data quality before using
3. Cache validated data for performance
4. Log all data quality issues for debugging
5. Provide actionable error messages to users
